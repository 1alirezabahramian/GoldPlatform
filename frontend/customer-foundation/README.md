# FE-01 — Customer Frontend Foundation

## هدف

ایجاد پایه‌ای واقعی و مستقل از فریم‌ورک برای پنل مشتری، بدون انتخاب حدسی React، Vue، Next، Nuxt یا هر فناوری اصلی دیگر.

## منابع حقیقت

1. `docs/00_PROJECT_MEMORY.md`
2. `docs/api/customer-v1.openapi.yaml`
3. قراردادهای Merge‌شده CP-01 تا CP-18

## اصول الزامی

- رابط کاربری فارسی و RTL است.
- پیچیدگی Backend، Ledger و Kimia در UI نمایش داده نمی‌شود.
- مقادیر مالی از API به‌صورت رشته دریافت می‌شوند و Frontend نباید آن‌ها را به `float` تبدیل کند.
- Coin و Currency باید Dynamic باقی بمانند.
- Money، Gold، Coin و Currency دارایی مالی هستند.
- Custody دارایی فیزیکی است و جدا نمایش داده می‌شود.
- شناسه‌های داخلی Kimia و دیتابیس نباید عنوان اصلی رابط کاربری باشند.
- همه درخواست‌های پنل مشتری باید از قرارداد `/api/v1/customer` پیروی کنند.
- `X-Request-ID` برای خطاهای پشتیبانی نگهداری شود.
- پاسخ‌های Customer API نباید در Cache پایدار مرورگر ذخیره شوند.

## فایل‌ها

- `tokens.css`: متغیرهای پایه RTL، تایپوگرافی، فاصله‌گذاری، دسترسی‌پذیری و White-label.
- `terminology.fa.json`: واژگان تأییدشده انسانی برای رابط مشتری.

## مرز این Stage

این Stage فریم‌ورک Frontend انتخاب نمی‌کند، صفحه نهایی تولید نمی‌کند و هیچ Business Rule مالی جدیدی نمی‌سازد.

## تصمیم معماری لازم برای Stage بعد

پیش از ساخت Application Shell باید فناوری اصلی Frontend با تأیید مالک پروژه مشخص شود. گزینه انتخاب‌شده باید:

- TypeScript داشته باشد؛
- RTL و فارسی را به‌صورت First-class پشتیبانی کند؛
- قرارداد OpenAPI موجود را مصرف کند؛
- برای White-label و چند برند مناسب باشد؛
- پیچیدگی مالی را در Backend نگه دارد.
