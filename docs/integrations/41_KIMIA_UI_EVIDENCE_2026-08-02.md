# GoldPlatform — شواهد رابط کاربری Kimia برای تعریف جنس و حساب

**تاریخ ثبت:** 2026-08-02

**وضعیت:** شواهد مشاهده‌شده؛ فاقد هرگونه تغییر زنده در Kimia

**مالک دانش دامنه:** علیرضا بهرامیان

**منابع تصویری:** فرم «جنس جدید» و فرم «تعریف حساب/کاربر» در Kimia

## هدف

ثبت اطلاعات قابل مشاهده در فرم‌های واقعی نرم‌افزار حسابداری Kimia و تعیین اثر آن‌ها بر معماری GoldPlatform، بدون حدس‌زدن قرارداد API یا منطق مالی.

## سطح اعتبار شواهد

- مواردی که مستقیماً در تصویر دیده می‌شوند، «تأییدشده در رابط کاربری Kimia» هستند.
- قابل مشاهده بودن یک فیلد در نرم‌افزار دسکتاپ، ثابت نمی‌کند همان فیلد در API عمومی Kimia قابل خواندن یا نوشتن است.
- اعداد نمونه مانند `153`، `522` و `449` نباید Hard-code شوند.
- نگاشت فیلدهای UI به API فقط پس از تطبیق با Swagger یا خروجی واقعی قطعی می‌شود.

## 1. فرم تعریف جنس

شش نوع قابل انتخاب مشاهده شد:

1. ساخته
2. کالای غیرطلایی
3. ارز
4. خدمات
5. سکه
6. سکه غیره

فیلدهای مشترک شامل نام، تصویر، گروه جنس، کد، یادداشت و انتخاب نوع جنس است. «گروه جنس» با «گروه حساب مشتری» یک مفهوم مستقل است.

### ساخته

- عیار؛ نمونه `750`
- مبنای محاسبه فی: وزنی/عددی
- ارز دریافتی
- سایزبندی، پلاستیک، سنگ و ارزش افزوده
- سازنده، فی و درصد فروش نقدی

### کالای غیرطلایی

- مبنای محاسبه فی، واحد وزن و ارز دریافتی
- ارزش افزوده، سازنده، فی و درصد فروش نقدی

### ارز

- اعتبار، نماد، ارز پولی‌کردن و ارز تبدیلی

### سکه و سکه غیره

- عیار؛ نمونه `900`
- وزن یک عدد، نماد و ارز تبدیلی

### خدمات

- مبنای محاسبه فی: وزنی/عددی

## 2. فرم تعریف حساب/کاربر

فیلدهای قابل مشاهده:

- کد؛ نمونه `522`
- نام؛ نمونه «کاربر تستی»
- گروه؛ نمونه «تکفروشی»
- کد ملی، عیار تسویه حساب، همراه، تلفن و یادداشت
- بخش‌های مدت و اعتبار، مالیات، نشانی، تاریخ‌ها و تنظیمات
- `ID` مستقل؛ نمونه `449`

## 3. نتیجه قطعی درباره Code و ID

`Code` و `ID` مستقل‌اند:

- `AccountId` شناسه اتصال پایدار Kimia است.
- `AccountCode` کد نمایشی/عملیاتی است و نباید جای شناسه پایدار استفاده شود.

همین اصل درباره محصول نیز برقرار است: شناسه داخلی پایدار و کد کالا قابل تغییر/جست‌وجو است.

## 4. اثر معماری

- جدایی `kimia_id/external_id` از `account_code/code` باید حفظ شود.
- گروه حساب و گروه جنس Dynamic و مستقل‌اند.
- مدل Catalog نباید همه انواع جنس را به یک ساختار تخت و اجباری تبدیل کند.
- تفکیک API میان Product، Coin و Currency حفظ می‌شود.
- هیچ نگاشت میان شش نوع UI و `ProductDto.Type` فقط از روی تصویر ساخته نمی‌شود.
- مشتری نباید ID، AccountType، GroupId، ارز پولی‌کردن یا عیار تسویه حساب را ببیند مگر نیاز کسب‌وکاری تأیید شود.

## 5. موارد نیازمند تطبیق API

1. تطبیق `ID=449` با `AccountId` و `Code=522` با `AccountCode` در خروجی واقعی.
2. فیلد و Endpoint واقعی گروه حساب.
3. نگاشت شش نوع جنس UI به منابع/Typeهای API.
4. قابلیت خواندن فیلدهای تخصصی از Product/Coin/Currency endpoints.
5. شناسه پایدار جنس و تفاوت آن با کد فرم.
6. امکان خواندن/نوشتن اعتبار، مالیات، نشانی، تاریخ‌ها و تنظیمات از API.

## تصمیم اجرایی

- تصویرها شاهد UI هستند، نه قرارداد Write API.
- هیچ Migration، DTO، Enum یا قانون مالی فقط بر اساس آن‌ها تغییر نمی‌کند.
- هر فیلد جدید فقط پس از مشاهده در Swagger یا خروجی واقعی وارد قرارداد فنی می‌شود.
